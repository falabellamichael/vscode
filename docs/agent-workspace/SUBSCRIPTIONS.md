# Agent subscriptions

Fresh Devin sign-in offers **Browser Sign-In** (automatic return to Signal-C) and **Browser Code** (recovery when the browser opens but sign-in does not finish). For Browser Code, complete account selection and approval on Devin's page, then paste the authorization code it shows into Signal-C's private input. This mode omits the loopback redirect and exchanges the code with the same fresh PKCE verifier; it does not import a CLI token or change the CLI's saved account. Cancelling either picker or the notification preserves a previously saved subscription account, and cancellation or timeout releases the attempt for retry. Use **Sign In Again** to choose Browser Code when a saved connection already exists.

The fallback follows Devin's current public `/auth/cli/continue` page, which displays a copyable code when `redirect_uri` is absent. Devin also documents manual authentication recovery in its [official CLI troubleshooting](https://docs.devin.ai/cli/troubleshooting). The authentication fixtures cover the code exchange, private input, validation, cancellation, timeout, retry and existing account preservation with synthetic credentials. Extension compilation and strict fixture type checking are separate checks; these fixtures do not establish that a real account can sign in or access a model.

Devin authentication listens for changes to its existing SecretStorage entry, so Agents and IDE windows sharing that storage receive account sign-in, replacement and removal events without restarting. Each window compares its last known session before emitting an event; its own completed writes and repeated unchanged notifications do not produce duplicates. A detected account change from another window cancels that window's pending sign-in, including its method or code prompt. Disposed providers stop observing storage. This uses the editor's existing secret-storage event channel and does not copy credentials into another profile or CLI store. Provider fixtures exercise synthetic shared storage; the native smoke check below exercises actual editor storage and both windows with synthetic accounts. Neither establishes real account access.

Before saving a replacement sign-in, the provider also checks that the account currently in storage still matches the one present before browser authorization. This catches a sign-out or replacement already visible in storage while its event is queued behind the local write operation. This is a consistency check over the existing SecretStorage API, which does not provide an atomic transaction across windows.

Devin browser sign-in reports its current phase in the cancellable notification: waiting for browser approval, exchanging the authorization code, then saving the sign-in securely. The extension host log records only the browser/code waiting and exchange phase names, without callback URLs, codes, or tokens. A browser page opening is not proof of a completed sign-in; a stuck waiting phase means the loopback callback has not completed, while an exchange failure occurs after browser approval. These messages diagnose the handoff and do not change provider entitlement or bypass approval.

Cancellation and the sign-in timeout also release an attempt while the editor's browser-opening call is still pending. The loopback listener closes and the provider can start a fresh sign-in without waiting for that old browser call to settle. A late browser success or failure cannot resume the cancelled attempt or replace the newer account. When Devin has a saved connection or reports a connection problem, selecting **Devin Subscription** offers **Retry Connection** and **Sign In Again**. Retry reuses the saved sign-in. Sign In Again explicitly starts a fresh browser flow even if an account is already saved; the authentication extension replaces that account only after sign-in succeeds. Cancelling the picker makes no change, and a failed or cancelled browser flow preserves the previous account. An unavailable Devin executable still needs to be corrected before its native agent can run.

The Devin Subscription row shows the current connection status when the picker opens: checking, signed out, browser sign-in in progress, saved sign-in connecting, saved sign-in with the agent unavailable, connection needing attention, or a ready model count. Ready requires acknowledgment of the current saved credential by the registered provider and a nonempty catalog in the agent host's root state. It does not establish model entitlement. Reopen the picker to refresh the displayed status. Selecting Devin Subscription retries with the saved account and refreshes an empty catalog without another browser sign-in. A delayed acknowledgment after sign-out, provider removal, or a host restart cannot mark the replacement connection ready; a signed-out host receives credential revocation even when no previous credential acknowledgment is known.

Stop covers turn preparation, including initial connection and conversation restoration. Stopping before process launch prevents the prompt from starting; stopping a pending initialization or load closes that client and ignores its late response. A competing send or model change cannot modify a preparing turn's workspace or model. During a running prompt, repeated Stop is idempotent and its two-second force-close deadline is tied to that exact client and turn. New permission requests after Stop are declined, and the turn remains cancelled even if a normal completion races with cancellation. If the client ignores Stop, the next explicit message reconnects to the same saved native session, workspace, and selected model; it does not resend the stopped prompt automatically.

A follow-up explicitly sent after Stop waits for the cancelled operation's cleanup rather than failing while that operation is still closing. Graceful cancellation reuses the connection; forced closure restores the same native session before the follow-up is sent once. Stop can cancel a waiting follow-up, and a third explicit send remains behind both cancelled operations until cleanup finishes. Sign-out, account replacement, chat release or disposal, and provider shutdown cancel waiting work. History reads return the current transcript while a send owns cleanup or reconnection instead of starting a competing replay. Host-queued messages stay under the host's existing controls and are not drained by this handoff.
